# 从数据读到交易解释

这份导读解释 `src/quant_core/` 的真实实现；源码按 [根规则](../../AGENTS.md#按业务语义分层解释qc-014唯一主规范)分层说明职责、调用约定、业务阶段和易错边界，本页承载跨函数流程与推导。禁止维护另一份逐渐分叉的“教学版代码”。

1. `application` 装配固定时钟、市场日历、数据入口、事件存储和 FakeBroker；`cli` 只解析命令与呈现结果。
2. `contracts` 在边界处校验类型和共同语义。`data` 先按决策时点选择版本，再执行质量规则；读取顺序不能反过来选中后来修订值。
3. `universe` 使用历史证券身份和资格。剔除候选不会改写已有账户仓位，停牌旧仓仍需保留并说明。
4. `factors` 使用总回报序列，动量读取 t-21 和 t-252，低波动从 61 个价格构造 60 个收益；不足历史在此明确暴露。
5. `signals` 在同日合格证券间评分；证券稳定 ID 提供确定排序。`regime` 记录状态依据，不能把观察规则暗中变成仓位决策。
6. `portfolio` 将目标得分变成受上限约束的整股数量；已有仓位和未完成订单都参与计算。候选不足或约束不可行允许留现金，不重新归一化突破单票上限。
7. `risk` 在目标和提交前检查对应操作。`execution` 先持久化稳定意图再调用 Broker；超时进入未知状态，恢复先核对再决定是否继续。
8. `ledger` 只处理具有唯一身份的交易事实。重复事件不能重复扣现金或增加持仓，公司行动避免价格调整和股息双记。
9. `monitoring` 比较任务、数据和账户事实。`reporting` 从留存数据串起“原始价格→因子→得分→状态/约束→目标→订单→成交/费用”，不能编造缺失步骤。

复杂函数和公共入口按需说明职责、关键输入与单位、返回及失败含义、调用前提和状态副作用；简单函数无需套用长模板。对注释含义的复核必须查看真实分支；docstring 存在性通过不能证明说明正确或边界完整。

## 在当前调用处辨认对象

以下沿 `application.run_demo` 的真实路径说明对象衔接；同一函数在校验、研究中还会复用，不能把这里的用途当成唯一用途。源码保留相应局部摘要，本页承载跨模块关系。

| 对象与建立位置 | 当前含义与去向 | 是否已经改变交易事实 |
|---|---|---|
| `snapshot = build_snapshot(...)` | 从完整合成行情/历史主表按决策时刻筛选并校验，供因子、评分和目标共用 | 只是这次决策的输入，不是账户 |
| `factors = calculate_factors(...)` | 每只证券各因子的原始值或缺失原因，动量与低波动尚未变为同一尺度 | 纯计算，交给评分并另存证据 |
| `signals = score_factors(...)` | 双因子共同有效的证券、百分位综合分、排序及排除原因 | 排名用于选目标，不是下单指令 |
| `target = build_portfolio(...)` | 基于决策初态/原始收盘的希望持仓，包含需保留的不可交易旧仓；基础权重固定，不按候选数归一化 | 目标尚未成交，不改变传入账户 |
| `intents = plan_orders(...)` | 执行时根据目标、实际仓位和订单历史计算候选买卖意图，再受预算限制 | 仅内存计算；空列表不保证目标完成 |
| `order = service.submit(...)` | 在账户锁内保存意图、核验风险、调用 Broker，返回当前订单记录 | 可写内部库并向 Broker 发请求；OPEN/PARTIAL不等于全部成交 |
| `broker.fill(...)` 后 `service.recover()` | 演示先在独立 FakeBroker 记成交，再导入事件更新内部现金/股数，核对两边事实 | 两个不同的写入步骤；失败不抹掉之前已成交/已提交记录 |

`risks` 逐单累积独立风控判断并写 `risk.json`，属于审计证据，当前 `render_report` 并不读取它。提交仍由执行服务重新核验，不能把审计记录当执行批准。`reporting` 接收最终账户、订单、目标及其他结构化结果生成文字，不反写账目。

## 同名变量的口径与局部索引

- `score_factors` 中的 `values[证券ID][因子ID]` 存原始数值；`components` 使用同样的索引，但存[0,1]百分位。`eligible` 是两种因子都有效的证券ID列表，两次排名共用它；`setdefault` 为每只证券建立内层表后继续累积，不覆盖前一因子。
- `build_portfolio` 的 `nav` 是决策时账户净值（NAV，现金加原始价持仓市值，美元）；`reserved` 是必须保留的旧仓市值，`allocated` 在此基础上逐只增加目标市值。它们是分配口径，不是实际扣现金。
- `plan_orders` 中的 `effective` 是本地「证券ID→实际股数+挂买余量−挂卖余量」，用于算目标缺口。`risk_quantities` 是另一本地数量表，只加买入占用，不扣尚未成交的卖单；它用于风险估值，两者不能合并。
- `desired` 存批准目标股数，`delta=desired-effective` 的正负分别代表需买/需卖。某笔订单的 `remaining` 是委托总量减已成交量，不是目标缺口。原账户持仓不因这些本地表的变化而改变。
- 规划的 `cash` 从已确认可用现金起步，扣未完成买单和本轮新买单预留；`turnover_used` 则是已真实成交的买卖美元总额，随后 `used_turnover` 加入挂单及新计划占用。换手比例的分母是固定 `target.nav`，卖出收入不抵销换手。
- `validate_run` 的 `actual_factors` 表示重算因子，`replay_run` 的 `actual` 则是新库重建账户；`expected` 来自旧运行导出文件，仍需被核对，变量名本身不表示独立真相。在执行服务 `_recover` 中，`actual` 才是券商独立账户，`expected` 是内部事件账本算出的账户。

原始执行价格以美元/股计，研究总回报价格用于因子/标签；ADV在当前演示中为决策已知的最近20交易日平均成交股数。比例字段是小数，例如0.045是净值的4.5%；主表是否有效、报价是否可用仍须按相应入口的时间规则检查，规划和风控现均对全部风险占用证券核验当时已知最高修订与唯一有效行业，不以目标补造主表。

## 本项目中几种库操作的效果

Pydantic 的 `model_validate` 把输入字典按模型校验，`model_dump(mode="json")` 转为JSON可序列化字段而不写文件，`model_copy(update=...)` 默认浅复制且不重新校验更新值。测试常故意用后者构造不合法对象，再检验边界是否拒绝；不能把复制等同验证。嵌套容器是否独立还需看调用处是否显式建立新字典。

资金预算用 Decimal（十进制金额）计算，比例经 `str` 转换以免引入二进制浮点尾差；整股额度按当前非负预算向下取整，余款留现金。`get(..., 0)` 在持仓表可代表未持有，在ADV表可代表没有可用流动性额度，在价格/行业资料中却不能普遍拿零掩盖缺失；源码在这些不同作用处分别解释。

SQLite适配器 `_db` 的生成器上下文在进入时开连接、`yield`交给调用者，正常退出提交当前事务、异常回滚当前事务，最后关连接。跨多次方法调用的账户锁由执行服务协调；已经提交的较早事务不随后一次失败回滚。备份工具的 `closing` 只保证关连接，不能把所有 `with` 都理解成同一种事务或锁。

## 恢复 journal 与监控参数

SQLite 的 `journal()` 返回按真实写入先后排列的 `JournalEntry`：意图持久化、订单投影、输入事件和公司行动都在原事务中留痕。回放以初始账户为起点按该序列重新执行；尤其不能将拆股/股息统一挪到成交前后。`apply_action(action, at)` 的 `at` 是显式 UTC 处理时刻，区别于行动实际发生和首次可用时间。相同成交的不同 event_id 封装保留证据，但唯一经济事实只计一次。

`monitoring.assess_health` 读取账户、目标、对账、订单，以及显式 `at`、`heartbeat_at`、`provider_at`、`data_good`、`factor_coverage`、`completed_steps`；不会读取系统时钟或发送网络通知。必需完成阶段是 data、factors、portfolio、execution、reconciliation。演示心跳超过 60 秒或来自未来告警；来源时钟绝对偏差超过 30 秒告警；双因子覆盖率低于 80% 产生观察告警。质量、对账、未知/拒单、任务缺失为关键告警；目标偏离只报告事实，不触发强制补单。

告警结构保留 code、severity、message、at、owner、acknowledged_at；未指定处置人或未确认时保持空值。当前输出 `alerts.jsonl`，真实独立通知通道、值守及确认流程尚未配置，不能以离线告警文件代替运营验收。上述阈值是固定演示规则，修改时同步该函数测试和本页；精确备份命令见 backups-migrations 运行手册。

## 报告重生的稳定顺序

报告由结构化事实生成。字典写入 JSON 时可以按键排序，重新读取后的插入顺序因此可能与首次内存对象不同。`reporting` 对市场状态 evidence 与排除原因 exclusions 采用 `json.dumps(..., sort_keys=True)` 展示，保证同一事实在首次生成、持久化后重生及回放时得到相同文字；不能通过删除字段或降低报告全文相等断言解决顺序差异。
